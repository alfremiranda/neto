One entry in an account’s ledger. The five sibling rows each show one KIND of thing in its own view; this one shows whatever the account did, in date order, so a single row has to carry an income, an expense, both legs of a transfer and a social-security payment. That is why the leading mark is a nested LedgerEntryIcon swap and not an axis. Six entry types times the axes below would be sixty variants for a fact the entry already carries. Three axes, and the matrix is deliberately sparse: · Device — Desktop edits and deletes in place; Mobile opens RowActionsSheet behind one button. · Flow — Credit prints the sign and paints the amount fg/provision; Debit leaves it fg/default. This is the one thing the siblings never needed, because each of them only ever moves money one way. · State — Default, Scheduled, Confirming, Opening. Confirming is Desktop only: it is the inline delete confirmation, and Mobile confirms inside the sheet. There is no Pressed, which the siblings do have, because this row has no pressed styling in code — the mobile tap opens the sheet and nothing else happens. Scheduled is a state of the ENTRY, not of the row: the whole row drops to 60%, the mark becomes the clock whatever the type underneath, and the “Programado” badge appears on the metadata line. THE BADGE SITS ON THE METADATA LINE, not beside the description, and that is the row family’s answer rather than a preference. The first build put it next to the description and capped the description with maxWidth so the badge could never be squeezed. That cap cannot survive: maxWidth is one of the few properties Figma refuses to override per instance, so a cap authored for a 603 row still truncated at 942, where the account page actually uses it. outcome-itemrow had already solved it — description alone on its line, FILL, truncating, no cap; badges and date below as chips that hug. It adapts to any width because nothing is pinned. State=Opening is the account’s STARTING balance, and it is a row rather than the strip it used to be above the list. That is the whole change: as a strip it had its own background and its own edges and read as a lid on the table; as a row it takes the same rules, the same left rail and the same right edge as the movements it explains, so the card is one table. It sits LAST, because the ledger runs newest first. It carries the same mark and the same trailing actions as every other row — Alfredo’s call on 2026-09-01, and the right one. The first build replaced both with blank spacers on the reasoning that a starting balance is not a movement, which kept the columns aligned but made the row read as a footer that had lost its furniture. Giving it a mark of its own (LedgerEntryIcon Type=opening: a wallet on the neutral tint) says what it is instead of saying what it is missing, and keeping the actions means the whole column behaves the same way down the card. It still carries no date and no running balance: at the opening, the amount IS the balance. OPEN for Dev — “eliminar” has no target here. A starting balance is a FIELD on the account (Account.startingBalance), not a ledger entry, so the pencil should open the account edit sheet and the bin has nothing to delete; clearing it means setting the field to null, which is an edit. Either the bin goes on this row or it means “borrar el saldo inicial”, and that is a product decision, not a design one. Flow is INERT on Opening and it is minted only at Flow=Debit. A starting balance has no direction. The alternative was two identical variants to keep the matrix square, which is a variant nobody maintains. Mobile RESTACKS into three lines — amounts, description, metadata — and again the family got there first. At the account page’s 346 the single-line desktop shape has to fit a description, a date, an amount column, the mark and an action: it cannot, and something has to truncate. Stacking gives the text the full width instead. Desktop keeps one line. Mobile’s action is Icon Button Size=XL (44), not LG. 44 is the 2.5.5 touch target and it is what the sibling rows use on Mobile. Desktop stays LG (36), where there is a pointer. On Desktop the amount block HUGS its content and its children are right-aligned. It was pinned to 104 until 2026-09-01 on my reasoning that a leading “+” would otherwise shift the column between neighbouring rows. That reasoning was wrong and I never measured it: with right alignment the “+” extends LEFTWARD, so the right edge never moves. Measured after Alfredo changed it — every Default, Scheduled and Opening row lands its right edge at the same x, and the pin was solving a problem the alignment already solved. The pin also had a cost it could not pay: `-USD 12.534,00` at Amount/Base measures 116 and wrapped to two lines inside 104, so a USD account got a different row height from a COP one. Hugging fixes that for free, at any currency and any string length. On Mobile the amounts move into the stack and none of this applies. CLOSED 2026-09-01 — the six differences this row opened against the code are all implemented (`a082dbfa`, `03173232`): the mobile restack, the 44px mobile target, Body/Base-Emphasis, Amount/Micro, the LG desktop actions and the badge on the metadata line. Dev flagged three of them as stale here; it was six. Verified in the source, not taken on trust. One difference is left and it is small: the metadata line orders it [date][badge], the family and this component order it [badge][date] — outcome-itemrow puts its chips before the date. Not worth a ticket on its own; fold it into the next thing that touches the row.
