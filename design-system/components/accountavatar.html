An account’s identity mark: the tinted circle in account/{hue}/surface with the account-type glyph in account/{hue}/accent. This is the pairing the colour picker is choosing, and the only place the surface token is used. Two axes. Colour is twelve. size is SM (24) and LG (40) — SM because both consumers needed it, AccountCard’s header and AccountSummaryCard’s. MD (32) exists in the code’s cva and is deliberately NOT minted here: nothing uses it yet, and a variant with no consumer is a variant nobody maintains. The account TYPE stays a nested swap (Icon Account: Bank Account · Cash · Credit Card · Savings) rather than a variant axis. Twelve colours times four types would be 48 variants for two independent decisions — colour is the user’s, type is the account’s. THE COST OF THAT NESTING, found 2026-09-01 and worth knowing before you change a type. The accent is bound on the glyph’s VECTOR, three instance levels down, and each account type resolves to a DIFFERENT vector. So switching Account Type on an instance lands on a glyph that still carries the icon library’s own fg/subtle, and the account colour silently disappears. Figma has no inheritance; the code does — it sets --account-accent on the span and the glyph inherits it — which is why this is a Figma-only trap. Whoever switches the type on an instance must re-bind that glyph’s fill to account/{hue}/accent. Every instance in the file is bound correctly today. Glyph contrast is verified against its own tint in both modes: Light floor 3.07:1, Dark floor 8.02:1. A filled glyph is a graphic object, so 1.4.11 applies — the rule the favourite star was got wrong on. The twelve are ordered by HUE ANGLE, measured from each accent’s Light value: orange 21° · amber 32 · lime 86 · green 142 · emerald 161 · teal 175 · sky 200 · blue 221 · indigo 243 · purple 271 · pink 333 · rose 347. Read as a ramp it lands almost back where it started, which is what a wheel does. The order is not decoration. Neighbours are the pairs that measure closest — orange/amber at 11°, emerald/teal at 14 — and putting them side by side is what lets someone SEE they are two, instead of meeting one of them six positions later and reading it as the same colour twice. The CHILD order in the set is that ramp. Figma’s properties panel is not: it keeps its own option order (purple first, today), it has done so since before the size axis was added, and reordering the children does not re-derive it. The description used to claim the panel was sorted too. It never was.
